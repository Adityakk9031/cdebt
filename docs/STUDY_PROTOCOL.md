# Validity study protocol: does familiarity predict verified comprehension?

Status: **protocol only; not run.** The maintainers run it. This document is the pre-registration:
the hypothesis, the design and the analysis are fixed here before any data exists. Any deviation
must be listed in the write-up with the reason.

## 1. Question and pre-registered hypothesis

cdebt's central claim is that its questions measure whether someone understands code. The
backtests (`docs/RESULTS.md`, `docs/RESULTS_MATCHED.md`) could not test that, because the dataset
has no quiz results. This study tests the minimum credible version of the claim:

> **H1 (primary, one-sided):** For code in a real repository, the proportion of cdebt probes
> answered correctly is **higher when the participant reports having written or reviewed the code
> ("familiar") than when they report never having seen it ("unfamiliar")**.

If H1 fails, the questions do not even separate people who know the code from people who don't,
and cdebt's "verified" label means very little. A positive result is necessary, not sufficient
(see section 7).

Secondary (descriptive, no multiplicity claim): wrote vs reviewed; by probe kind (runtime,
call-graph, constant); by whether the unit is mostly AI-attributed (>= 50% of its lines) or mostly
human; effect when responses marked "consulted" are excluded.

## 2. Design

1. A coordinator picks a repository the participants actually work on (ideally one where several
   people each wrote or reviewed different parts, and some parts none of them touched).
2. `cdebt study init --repo R --n 12 --seed S` generates a **fixed set of questions** (at most two
   per file, drawn from the highest-debt files) and writes two files:
   - `study.json`: questions only, no answers. Safe to send to participants.
   - `study.secret.json`: the coordinator's HMAC key and answer MACs. **Never send it.** Answers
     are not recoverable from `study.json` even by brute force over the options.
3. Each participant runs `cdebt study run study.json --team <label>` (about 10-15 minutes, no
   sandbox needed). For every question they give an answer, say whether they **wrote**,
   **reviewed** or **never saw** the code the question is about, and say whether they **looked
   anything up or asked anyone (including an AI)**. They are told not to. No feedback on
   correctness is shown (avoids learning effects).
4. Participants send back one `response-<random>.json`. It holds a random 8-hex id, an optional
   team label, the date, and the answers. No name, host, account or time of day.
5. The coordinator runs `cdebt study analyze study.json responses/ --secret study.secret.json`.

## 3. Sample

Planning numbers from `docs/study_power.json` (generated by `cdebt study power`; the proportions
and the intraclass correlation are **assumptions**, not measurements): to detect 0.70 vs 0.55 with
one-sided alpha 0.05 and power 0.80, 12 questions per participant and an assumed ICC of 0.10
(design effect 2.10), about 271 responses per group, i.e. about **46 participants**.
Recruit at least **30 participants from at least 3 teams** to run the study at all; below 5
participants in any cell the tool suppresses that cell, and with fewer than 5 participants
overall it refuses to give a contrast. If fewer than ~46 are available the study is underpowered
for a 0.15 difference: say so, and report the interval rather than a verdict.

## 4. Analysis (fixed)

- **Grading:** deterministic HMAC comparison against the coordinator's secret; no human or model
  grades anything.
- **Primary statistic:** difference in proportion correct, familiar minus never-saw, over all
  responses; **95% CI by cluster bootstrap resampling participants** (2000 replicates, seed 0).
  H1 is supported only if the lower bound of that CI is above 0.
- **Sensitivity (reported next to the primary):** the same, excluding responses the participant
  marked as consulted.
- Naive Wilson intervals per cell are shown for orientation only (they ignore clustering).
- No participant-level or per-person result is ever printed. Cells with fewer than 5 distinct
  participants are suppressed. A team label is shown only for teams with >= 5 participants.

## 5. What would change the conclusion

- H1 supported and the effect survives excluding consulted responses: the questions separate
  familiar from unfamiliar code at the level measured. Report the size and CI.
- H1 not supported with an interval that excludes a difference of 0.10: the probes do not
  discriminate; the project should say so in its README and reconsider the "verified" label.
- H1 not supported but the interval is wide (underpowered): inconclusive; collect more data.
- Opposite direction: investigate item quality (for example, constants that are guessable, or
  call-graph questions that reward test-file knowledge) before drawing any conclusion.

## 6. Ethics and privacy

- Participation is voluntary and the instructions say so. Do not run this on a team in a way
  that lets management see who did well: the tool has no per-person output, and the coordinator
  must not share raw response files with anyone outside the study.
- Familiarity is self-reported; consulting is self-reported and under-reported if people feel
  watched. That is a known limitation, not something to enforce.
- cdebt measures code and teams, never individuals. Do not add a leaderboard.

## 7. Limits of what this can show

- It tests discrimination between self-reported familiar and unfamiliar code, not that
  "verified" means someone can safely change the code.
- Self-report can be wrong in both directions (someone reviewed code in 5 minutes and feels
  familiar). Effect sizes are attenuated by that.
- Questions are about behaviour that can be computed (return values, references, constants), so
  the study says nothing about design-level understanding.
- One repository and one team mix cannot generalise; report which was used.
- A participant can still look things up or paste the question into an AI. The "consulted"
  self-report and the sensitivity analysis only reduce the damage.

## 8. Reporting

Publish the study file (questions), the aggregate output of `cdebt study analyze --json`, the
repository and commit, the number of participants and teams, and every deviation. Do not publish
response files.
